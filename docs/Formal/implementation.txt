# Stage 3 — Contributions, accounting and reconciliation

This is the largest business-critical gap.

## 3.1 Improve contribution records

### Current implementation

The system already supports:

- Manual contribution entry
- CSV import
- Cash, bank, M-Pesa and other methods
- M-Pesa references
- Receipts
- Individual PDF statements
- Basic charts

### Missing fields or behavior

- Contribution status
- Pending/confirmed/reversed state
- Adjustment relationship
- Correction reason
- Source account
- Reconciliation status
- Reconciliation date
- Transaction reference uniqueness
- Supporting document
- Contribution-period tracking
- Arrears and expected amount
- Configurable categories

### Implementation approach

1. Introduce configurable contribution categories.
2. Add transaction lifecycle states:
   - Pending
   - Confirmed
   - Reconciled
   - Reversed
3. Do not silently edit or delete confirmed transactions.
4. Use reversal and adjustment records.
5. Require a reason for corrections.
6. Record old value, new value and actor.
7. Add duplicate-reference detection.
8. Add supporting-document attachments.
9. Support daily, monthly, welfare, project and special collections.

## 3.2 Create a proper financial ledger

### Current limitation

The `Contribution` table represents money received but cannot provide full accounting.

### Required entities

- FinancialAccount
- FinancialTransaction
- TransactionCategory
- Expense
- Disbursement
- Adjustment
- Reconciliation
- SupportingDocument
- AccountingPeriod

### Implementation approach

1. Treat contributions as one source of financial transactions.
2. Record income and expenditure separately.
3. Define accounts such as:
   - Cash
   - Bank
   - M-Pesa
   - Welfare fund
   - Project fund
4. Use immutable transaction records.
5. Calculate balances from ledger entries.
6. Require supporting evidence for selected expenditure categories.
7. Add approval rules for high-value transactions if required.
8. Close accounting periods to prevent unauthorized historical changes.

## 3.3 Payment reconciliation

### Missing functionality

- Unmatched payments queue
- Manual member matching
- Duplicate detection
- Reconciliation notes
- Bank/M-Pesa comparison
- Reconciliation report

### Implementation approach

1. Store incoming payment events before assigning them to contributions.
2. Match by phone, reference, amount and member.
3. Move uncertain records into an unmatched queue.
4. Allow Treasurer to assign a member and category.
5. Require notes for manual reconciliation.
6. Audit every match and correction.
7. Prevent one provider transaction from being reconciled twice.

## 3.4 Financial reports

- Arrears report

- Income/expenditure statement
- Welfare-disbursement report
- Investment-spending report

3. Generate reports from the ledger.
4. Support screen view, PDF, CSV and Excel where appropriate.
5. Include report-generation timestamp and filters.
6. Restrict report access by role.
7. Audit sensitive exports.

### Stage 3 completion criteria

# Stage 7 — Loans (simple optional module)

## Decisions

- Module is **optional**: Admin / Super Admin toggle `loans_enabled` feature flag (default off).
- Workflow: Member applies (with guarantors) → Treasurer reviews (profile + contribution/welfare history) → Admin / Super Admin approves or rejects → Treasurer records disbursement and repayments on the ledger.
- Outstanding balance = confirmed disbursements − confirmed repayments (transaction-derived via `LoanLedgerLink`).
- **Skipped in v1:** interest/fees, contribution-ratio hard eligibility, immutable installment products, penalties, default workflow, full PDF statement suite.

### Admin-editable loan policy (when flag on)

- Max amount KES (default 50,000)
- Min guarantors (default 1)
- Require guarantor accept before approve (default yes)

## Implemented

- Models: `LoanApplication`, `LoanGuarantor`, `LoanLedgerLink`
- Actions: [`app/actions/loans.ts`](app/actions/loans.ts)
- UI: `/dashboard/member/loans`, `/dashboard/treasurer/loans/[id]`, `/admin/loans`, `/dashboard/executive/loans` (read-only outstanding report)
- Nav items appear only when `loans_enabled`
- Email notices via Resend for guarantor invite and decisions

### Stage 7 completion criteria

- Loan behavior matches the simple approved workflow and Admin policy settings.
- Applications and approvals are audited.
- Repayment balances are transaction-derived.
- Treasurer and Admin permissions follow the workflow above; Executive has read-only report.
- Simple outstanding report available to Executive.
