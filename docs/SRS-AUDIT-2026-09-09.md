## Immediate blockers
1. **Branch financial disclosure risk:** app/actions/finance.ts exports getBranchContributionSummary(principalId) from a 'use server' module with no session/ownership check. It returns member names, amounts and purposes. Derive the branch from the authenticated Principal and authorize every request. The summary also totals only the latest 100 records, so larger branches receive an incomplete total.
2. **Directory privacy is incomplete:** app/actions/directory.ts returns hidden attached members' names, relationships and Principal names as “summary-only” entries. Attached adults can grant themselves visibility through isSelf. Principal fields are always added to the allowed set, overriding configured restrictions. reviewAt is stored but not used in the listing. Derive viewer identity from session, truly omit hidden members, enforce Principal consent and child rules, and define review versus expiry.
3. **Activity audience enforcement trusts input:** app/actions/activities.ts listTodayActivities(viewer) checks that someone is logged in but uses caller-provided role/branch for filtering. Derive identity from the session, filter before take:40, reject unknown audiences. “Today” uses server-local midnight; undated-end past activities remain eligible indefinitely. Use the configured local timezone and correct date ranges.
4. **Document history can be permanently removed:** deleteRepositoryDocument and bulk delete in app/actions/documents.ts remove Storage objects and database rows, including versioned records. Archive referenced/history-bearing records; add retention/legal-hold checks and restore.
5. **Document upload/management scope needs tightening:** the signed-upload completion path accepts storagePath/versionGroupId/mimeType from the client without verifying object ownership, actual size/type or the issued upload. Replacement/status/deletion use broad staff-role gates without checking rights to the particular document. Validate stored objects and per-document scope.
6. **MFA hardening incomplete:** app/actions/mfa.ts beginMfaEnrollment overwrites the current secret and disables enabled MFA without verifying the existing factor. MFA secret is stored directly in the user record; no recovery-code flow found. Login checks enabled TOTP, but session/OAuth/direct-provider assurance must be tested and enforced consistently.
7. **Current validation fails:** npm run check fails at TypeScript, including directory return types, missing principalMemberId on SessionProfile, form-action return types, contribution filter types and chart tooltip types. The combined command therefore does not reach unit tests. Resolve before claiming a working release.

These are source-confirmed weaknesses or missing checks, not a claim that a live exploit was executed.

## Proposed implementation batches and completion tests
1. **Stabilize and protect:** fix compilation, authenticate every server action/query, derive actor from session, isolate branches, close directory leaks and secure MFA enrollment. Verify anonymous/inactive/other-branch/forged-role calls are denied.
2. **Membership and privacy:** configurable policy/status/relationship management, constrained visibility, child transition, transfer approval and Principal summaries. Verify no duplicate member IDs and no unapproved directory exposure.
3. **Payments and finance:** manual submissions/proof, correction workflow, active purpose management, protected official destination, obligations, allocation versioning, outgoing authorization and complete reports. Verify self-approval/duplicate approval/concurrent approval prevention, report totals and reconciliation.
4. **Resources and governance:** archive/restore, retention, version metadata/object checks, searchable folders/text, calendar list/audiences/logistics and secretary queues. Verify restricted downloads, file validation, version preservation and audience boundaries.
5. **Welfare/projects/notifications:** confidential beneficiary requests, configurable approval chain, project scopes, durable notification events and read state. Verify unauthorized officers cannot read confidential requests; all lifecycle events reach the correct recipients.
6. **Launch evidence:** regression, mobile/tablet/desktop and accessibility tests, staging database migration, storage/RLS verification, backup restoration and deployment smoke tests. Completion requires evidence, not percentage estimates.
